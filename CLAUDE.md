# Vibe OS

Платформа вайбкодинга для учеников онлайн-школы Eduson Kids: ученик в браузере пишет проекты (HTML/CSS/JS, Python, Node), общается с ИИ-агентом, который правит файлы проекта, запускает код в песочнице и публикует сайты. Есть панель администратора.

Состав: портал (`apps/portal`: React SPA + API на Fastify), root-координатор (`services/workspace-broker`), шлюз модели (`services/model-gateway`), файловый Runner на Go (`services/runner`), профиль агента DeepSeek Harness (`profiles`), инфраструктура (`infra`: nsjail, systemd, nginx, bootstrap). Процессы разделены по привилегиям (разные системные пользователи, Unix-сокеты, capability) — это граница безопасности, её не размывать.

## Принципы разработки — ОБЯЗАТЕЛЬНО

Касается всех этапов: код, схема БД, инфраструктура, сборка, тесты, настройка сервера.

- **Не изобретать велосипед.** Если задачу решает фреймворк проекта, его официальный плагин или зрелая распространённая библиотека — берём её, а не пишем своё. Своё пишется, только когда готового решения нет или оно не подходит по конкретной причине (безопасность, лицензия, заброшенность); причина записывается в описании коммита или в спеке.
- **Сначала возможности фреймворка.** Fastify: плагины, хуки, JSON Schema-валидация, декораторы, встроенный логгер (pino). React: штатные механизмы и библиотеки экосистемы. Не дублировать то, что фреймворк уже даёт.
- **Опираться на официальную документацию** используемых инструментов и на реальные, широко применяемые паттерны. Не выдумывать собственные схемы там, где есть устоявшаяся практика.
- **Антипаттерны не допускаются**: God-файлы, бизнес-логика в маршрутах, SQL вперемешку с HTTP, глобальное изменяемое состояние, «магические» строки и числа вместо констант и конфигурации, копипаста вместо общего модуля, правки сервера руками в обход описанной инфраструктуры.
- **Своя криптография и своя аутентификация запрещены.** Только проверенные примитивы и библиотеки (`node:crypto`, `@node-rs/argon2`, официальные плагины Fastify).
- **Быть строгим senior-разработчиком**: решения обоснованы, проверены и не оставляют технического долга молча.

### Известные самописные решения — заменить при доработке соответствующего места

| Сейчас | Заменить на |
|---|---|
| `rate()` в `apps/portal/api/server.mjs` (лимитер в памяти) | `@fastify/rate-limit` |
| `fields()` — ручная проверка тела запроса | JSON Schema в маршрутах Fastify (+ TypeBox для типов) |
| Ручная сборка заголовков `Set-Cookie` | `@fastify/cookie` |
| Самописная проверка CSRF-токена | `@fastify/csrf-protection` (проверку `Origin` сохранить) |
| `CREATE TABLE IF NOT EXISTS` при старте | Нумерованные миграции (инструмент миграций выбранного слоя доступа к БД) |
| Заголовки безопасности частично в nginx | Полный набор в nginx и/или `@fastify/helmet`, без дублирования |

## Архитектура бэкенда — модульный монолит

Внутри каждого процесса (портал, брокер, шлюз) код делится на модули по предметным областям; модуль = плагин Fastify с одинаковым устройством: `routes` → `service` → `repo`, внешние системы — через `adapters/`.

1. Зависимости только вниз: route → service → repo/adapter.
2. Маршрут — только HTTP (схема, вызов сервиса, ответ). Сервис не знает про HTTP. Репозиторий — только SQL.
3. Модули общаются через сервис соседнего модуля, не через его репозиторий и таблицы.
4. Сокеты, процессы, сеть, файлы проектов — только через адаптеры.
5. Зависимости передаются явно (фабрики `createXService({ repo, ... })`), без синглтонов внутри модулей.
6. Транзакция открывается в сервисе.

Микросервисы по функциям не вводим (решение 2026-10-28): разделение на процессы — только по границам привилегий.

## Продуктовые правила

- **Доступ в личный кабинет ученика и преподавателя создаёт только администратор через панель администратора.** Самостоятельной регистрации нет. Создание, блокировка, сброс пароля — операции админки (API `/api/admin/...` с проверкой прав администратора). Разовые скрипты заведения учёток (`apps/portal/api/bootstrap.mjs`) и файлы с паролями открытым текстом — наследие прототипа, подлежат удалению после появления этой функции.
- **Пароль задаёт сам владелец учётки по одноразовой ссылке-приглашению** — схема платформы KOTOKOD/Eduson (`docs/documentation/account-provisioning-2fa.md` там), одинаковая для учеников и преподавателей. Временных паролей, которые видит или придумывает админ, нет.
  - Админ создаёт учётку → система выдаёт ссылку `/set-password?token=…`; токен — 32 байта CSPRNG, показывается **один раз** в ответе API, в БД хранится только SHA-256.
  - Срок жизни ссылки — 48 часов; одноразовая (погашение под блокировкой строки/транзакцией, повтор невозможен).
  - У учётки не больше одного активного приглашения (частичный UNIQUE); перевыпуск отзывает прежние, история не удаляется.
  - Сброс пароля из админки = выпуск новой ссылки + немедленный отзыв всех сессий учётки.
  - Проверка и погашение ссылки отвечают одинаково для любой недействительной причины (без подсказок, существует ли учётка); на эндпоинтах — rate-limit.
  - Пароль проверяется правилами сложности при установке; хеш — Argon2id.
  - События `invite_created`, `invite_used`, `invite_revoked`, `password_reset`, `account_blocked` пишутся в журнал безопасности (без токенов и паролей).
  - Токен приглашения не должен попадать в логи nginx (query-string для `/set-password` не логировать).
- **2FA: обязательна для преподавателей и администраторов, у учеников её нет.** Схема KOTOKOD/Eduson: после установки пароля по приглашению — обязательная настройка второго фактора (TOTP или код на почту), коды восстановления.
  - До подтверждения второго фактора выдаётся только короткоживущий challenge-токен (5 минут), который не принимается как сессия; сессия создаётся заново после успешного кода.
  - Включение, отключение и сброс 2FA (сброс — только админом) завершают все сессии учётки и пишутся в журнал безопасности.
  - Перебор кода ограничен rate-limit и блокировкой учётки; TOTP и коды — готовыми библиотеками, не своей реализацией.
- Число учеников не зашивается в код, схему и конфиги (сейчас — 5, `CHECK(student BETWEEN 1 AND 5)`, UID `28000+N`/`29000+N`): новые учётки заводятся динамически.
- Vibe OS — самостоятельный продукт; интеграций с платформой Eduson/KOTOKOD не планируется.

## Репозиторий

- GitHub `ReyTayler/eduson_vibe_os`, **публичный**, ветка `main`. Секреты (`.env`, ключи, `master.key`, TLS), базы, дампы, данные учеников и их проектов в репозиторий не попадают ни при каких условиях.
- Код работает на Linux: окончания строк LF (`.gitattributes`).
- Unit монтирования хранилища хранится как `infra/systemd/srv-vibe-os-data.mount`, на сервер устанавливается под systemd-именем `srv-vibe\x2dos-data.mount` (обратный слэш недопустим в Windows).
- Полная копия прод-сервера с секретами — только в `C:\vibe-os-backup\` (вне проекта).
